# Synthetic data theory

> **Status: active · Updated: 2026-10-24**

Synthetic data is useful for this dissertation because real unsafe-to-safe
replacements are rare. The ID141 study found only ~114 unsafe-to-safe mitigation
transitions; SafeNet had 472 snippets and a 124-case knowledge base. That is
small for training modern models. Synthetic data can expand coverage, create
hard negatives, and make training cheaper.

But synthetic data alone will not convince reviewers. Training and evaluating
only on data generated by your own model is circular. The scientific formula is:

> Train/augment on synthetic + real; validate on real, held-out
> vulnerability-fix commits.

## 1. What synthetic data is good for

- Rare unsafe APIs and patterns. SafeNet focused on 18 APIs; more can be
  generated.
- Hard negatives: examples that look replaceable but are not.
- New Rust features: unsafe attributes, naked functions, extern blocks.
- Resource-management vulnerabilities. ID141 shows this category doubled; real
  data may be scarce.
- Cheap training of a lightweight ranker or LoRA adapter.
- Stress-testing the verifier: generate candidates that should fail compilation
  or MIRI.
- Preference data for DPO/ORPO: compile-pass vs compile-fail, MIRI-clean vs UB,
  safe vs unsafe.

Do not use synthetic data as the only final benchmark.

## 2. Four practical synthetic generation strategies

### A. Counterfactual injection from safe code

This is the strongest and most defensible strategy.

Take real safe Rust code and automatically inject an unsafe variant that is
known to be replaceable. The original safe code is the ground-truth replacement.

Examples:

- Replace `as` with `mem::transmute` for scalar conversions.
- Replace checked access with `get_unchecked`.
- Replace `Rc<RefCell<T>>` with raw pointers in a double-linked list.
- Replace a `Mutex<T>` global with `static mut`.
- Replace `u32::from_le_bytes` with `transmute`.

Advantages:

- Ground truth is real, compilable, and often tested.
- No LLM hallucination in the label.
- Thousands of examples can be generated cheaply.

Limitations:

- Injected unsafe may look artificial.
- Distribution may differ from real-world unsafe code.
- Use for training, not final evaluation.

### B. Template and rule-based generation

Use SafeNet's patterns, Rustdoc, safety properties, and contract types to
generate parameterized unsafe/safe pairs.

For each API and pattern:

- Generate type parameters, lifetimes, aliases, and contexts.
- Generate positive examples: replaceable.
- Generate negative examples: irreplaceable or conditionally replaceable.
- Generate encapsulation examples: safe wrapper with assertions.

This gives controlled, label-correct data.

### C. LLM-generated synthetic data

Use DeepSeek v4.1 or an open coding model to generate:

- Unsafe snippets for a given API and pattern.
- Safe replacements.
- Hard negatives that are semantically similar but irreplaceable.
- Project-like contexts with modules, structs, and call chains.

Every LLM-generated pair must be verified:

- Does it compile?
- Does MIRI pass?
- Do tests pass?
- Is the replacement actually safe?
- Does it preserve signature and semantics?

Only keep verified pairs. This becomes verification-guided synthetic data.

### D. Verification-guided preference pairs

Sample `k` candidate replacements from an LLM. Run compiler, Clippy, MIRI, and
tests. Label:

- Pass all → preferred.
- Compile but MIRI fails → rejected.
- Compile fail → rejected.
- Introduces new unsafe → rejected.

This gives preference data for DPO/ORPO or for training a ranker. It is cheap
and scientifically interesting.

## 3. How to validate synthetic data

Every synthetic example should have provenance and verification metadata:

```json
{
  "id": "...",
  "source": "counterfactual_injection | template | llm | real_commit",
  "unsafe_code": "...",
  "safe_code": "...",
  "api": "mem::transmute",
  "pattern": "scalar_type_conversion",
  "replaceability": "replaceable | conditional | irreplaceable | encapsulatable",
  "contract": "...",
  "verification": {
    "compile": true,
    "miri": true,
    "tests": true,
    "clippy": true
  },
  "difficulty": "easy | medium | hard",
  "project": "..."
}
```

For detection labels, use conservative rules:

- **Replaceable:** a known safe transformation exists and compiles.
- **Conditionally replaceable:** a safe replacement exists but may add overhead.
- **Encapsulatable:** unsafe is necessary but can be wrapped with checks.
- **Irreplaceable:** no safe replacement is known.

For irreplaceable examples, manual review is often needed. LLMs are bad at
proving impossibility.

## 4. How to use synthetic data scientifically

1. **Real seed set:** ID141 114+ transitions, SafeNet 472, RustSec/OSV, GitHub
   fix commits, Rustdoc.
2. **Synthetic set:** generated by the four strategies above.
3. **Split by project and time:**
   - Training: pre-2024 projects + synthetic.
   - Validation: 2024 projects.
   - Test: 2025–2026 unseen projects and vulnerability fixes.
4. **Ablation:**
   - Real only.
   - Synthetic only.
   - Real + synthetic.
   - Real + synthetic + RAG.
   - Full system.
5. Report both synthetic and real results; never claim superiority based only
   on synthetic.
6. Measure whether synthetic improves rare patterns without hurting common ones.
7. Release the generator and dataset if licenses allow.

## 5. Risks and how to mitigate them

| Risk | Mitigation |
|---|---|
| Synthetic distribution shift | Use a real hold-out; report distribution similarity. |
| LLM self-bias | Use a different model for generation vs synthesis, or open models. |
| Data leakage | Time/project split; keep test commits out of RAG and training. |
| Noisy labels | Verify with compiler/MIRI/tests; manual spot-check. |
| Artificial code | Prefer counterfactual injection from real safe code. |
| Reviewer skepticism | Frame synthetic as augmentation, not benchmark. |
| Cost | Local QLoRA, quantized models, cache verification. |
